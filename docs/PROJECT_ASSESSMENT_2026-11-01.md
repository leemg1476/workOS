# Work OS 프로젝트 현황·성과·성숙도 상세 평가

> 기준 시각: 2026-11-01 18:53경, Asia/Seoul. 이 문서는 [초기 명세](../init.md), 현재 저장소, 테스트 코드, [누적 작업 이력](WORK_STATE.md), 실행 중인 `workos-p0`의 읽기 전용 조회를 대조한 스냅샷이다. 실행 기록과 상태는 이후 달라질 수 있다.
>
> **판정:** Work OS는 세 가지 합성 업무로 지속 업무·검증·피드백·사용자 통제를 보여 주는 **로컬 기능 검증 단계**에 도달했다. 자연어 업무 등록과 텍스트 업무 연결도 구현했다. 그러나 실제 조직 데이터와 사용자의 실제 업무에서 효과가 검증된 제품은 아직 아니며, 100개의 서로 다른 업무를 추가할 때 공통 커널을 거의 바꾸지 않아도 되는 목표는 **일부 근거가 있지만 전체 범위에서는 미입증**이다.

## 1. 이 보고서에서 구분하는 증거

| 구분 | 의미 | 이 보고서에서의 취급 |
|---|---|---|
| 현재 로컬 서비스 | `workos-p0`의 API·DB·UI를 이번에 읽기 전용으로 확인 | 현재 시점의 상태. 데모 기록이므로 운영 실적은 아님 |
| 이번 테스트 | 별도 PostgreSQL/Redis와 임시 OpenSearch 인덱스에서 이번 보고서 작성을 위해 실행 | 테스트 명령과 결과를 제10절에 따로 기록 |
| 이전 수행 기록 | [WORK_STATE.md](WORK_STATE.md)에 기록된 당시 실행·화면·테스트 | 과거에 관찰된 결과. 이번에 같은 실행을 재현한 것과 구분 |
| 코드/테스트 정의 | 현재 소스가 구현하거나 테스트가 확인하도록 작성된 동작 | 코드 존재만으로 실제 운영 효과를 주장하지 않음 |
| 미커밋 작업 | 중지된 작업의 현재 작업 트리에 남은 여러 선행 업무 결합 코드 | 로컬 서비스에 적용되지 않은 진행 중 구현. 별도 표시 |

**데이터 경계:** 시장 수치·정책 문서·VOC와 평가 사례는 합성 자료다. `LIVE_LLM`은 모델 호출이 실제라는 뜻이며, 입력이 실데이터이거나 응답의 의미적 정확성이 검증됐다는 뜻이 아니다. 결정론적 검사 PASS, 사람의 채택, 업무 성과 개선도 각각 다른 사실이다.

## 2. 사용자가 원한 목표와 현재 판정

사용자가 요청한 흐름은 ① 사람이 자연어로 업무를 설명하고 ② LLM이 업무 구조로 변환하며 ③ 사람이 시각화된 구조와 결과를 확인하고 ④ Work OS가 업무를 계속 수행하며 ⑤ 자연어 또는 직접 수정 피드백을 통해 수행 능력을 개선하는 것이다. 여기에 업무가 10개, 100개로 늘어나더라도 Kernel 코드는 거의 수정하지 않는 구조가 추가 조건이다.

| 목표 | 현재 상태 | 확인된 근거 | 아직 증명되지 않은 것 |
|---|---|---|---|
| 자연어 → 업무 구조 | 구현됨 | LIVE LLM의 구조화 초안과 MOCK 초안, DAG 검증 및 버전 저장 경로 | 사용자의 다양한 실제 업무 설명에 대한 생성 정확도·안전성 |
| 사람이 구조 확인·수정 | 구현됨 | 단계·선행 ID·목표·기대 결과·기준 편집, 버전 이력, 자연어 변경 요청 | 복잡한 다중 업무 그래프의 전체 시각 편집·사용성 평가 |
| 등록 후 반복 수행 | 텍스트 범위에서 구현 | 수동/Cron Job, 입력 버전 고정, 재시도·사람 검토 | 실제 업무 데이터 자동 수집과 외부 시스템별 지속 실행 |

| 피드백 → 개선·명시적 적용 | 합성 데모와 텍스트 경로 구현 | VOC 고정셋 비교·적용/기각/롤백, 텍스트 사례 비교와 버전 결정 | 실제 사람이 판정한 품질 개선 및 실무 성과 |
| 업무 100개 추가 시 Kernel 안정성 | 제한된 구조 검증 | 서로 다른 이름·목표·1~3단계를 가진 100개 MOCK 텍스트 계약을 같은 실행기로 실행 | 100개의 서로 다른 데이터·도구·결과·이벤트·검증 요구 처리 |
| 결과와 이전 실행 비교 | 구현됨 | Work별 이력, 결과·검증 상세, 금융 비교와 VOC 사례별 개선·퇴행 | 버전이 다른 검사 결과의 품질 통합, 실제 업무 KPI 추세 |

## 3. 프로젝트의 현재 성숙도

아래 구분은 외부 인증 점수가 아니라 이 저장소의 관찰에 따른 판단이다.

| 영역 | 판정 | 근거와 경계 |
|---|---|---|
| 제품 흐름 | **로컬 데모 가능** | 세 데모가 Work 중심으로 구성되어 있고 결과·근거·상태를 볼 수 있다. 실제 사용자 업무는 아직 현 로컬 DB에 없다. |
| 데이터 모델·커널 | **기초 기능 검증** | Task/Job/Work/Run 분리, PostgreSQL 이벤트와 큐, 멱등성·상태 전이·STALE·재시도 검사가 있다. |
| 다중 업무 확장성 | **부분 검증** | 실행기·검증기 등록점과 100개 동형 텍스트 계약 검사는 있다. 도구·출처·출력 형태가 다른 업무 전반은 미검증이다. |
| 자연어 설계·텍스트 작업 | **제한된 기능 시연** | 초안·직접 수정·등록·사용자 검토가 있다. 현재 실행 입력은 사람이 제공한 텍스트와 연결된 선행 텍스트 결과다. |
| 지속 개선 | **고정 합성 평가 기반 시연** | 같은 입력의 비교, 퇴행 차단과 사용자 결정이 있다. 텍스트의 의미 품질은 자동 판정하지 않는다. |
| 외부 데이터 | **로컬 합성 연계** | PostgreSQL 읽기 전용 역할과 OpenSearch가 실제 프로세스로 동작하지만 실제 사내 시스템은 아니다. 검색은 문서 ID 중심이다. |
| 안정성 | **일부 장애 시나리오 검증** | lease 만료와 새 Run 재시도, 출처 누락·복구, 체크포인트 수동 재개를 테스트한다. 장기 운영 SLO나 부하 한계는 측정하지 않았다. |
| 보안·운영 | **로컬 단일 사용자 개발 환경** | 사용자·권한 관리, 운영용 비밀 관리, TLS, 운영 관측·장애 대응 체계는 검증 범위 밖이다. |

`P0/P1/P2`의 관계는 다음과 같다. P0의 주요 데이터·상태·큐·대시보드와 P1의 세 합성 시연은 동작 근거가 있다. 다만 초기 명세의 모든 운영 비기능 요구나 실데이터 연계까지 통과했다는 뜻은 아니다. P2는 읽기 전용 DB·검색의 **데모 어댑터**가 있는 상태이며 실제 사내 연동과 운영 경화는 남아 있다.

## 4. 현재 실행 환경과 실제 저장 기록

### 4.1 로컬 서비스

이번 조회에서 `workos-p0`의 API, UI, worker, scheduler, PostgreSQL, Redis, OpenSearch 컨테이너는 실행 중이었다. PostgreSQL은 Docker 상태상 healthy, UI는 HTTP 200이었다. `/api/health`는 DB `connected`, 검색 `OPENSEARCH / connected`, 데이터 `DEMO DATA`, 모델 선택지 `MOCK / LIVE_LLM`을 반환했다. API의 scheduler 필드는 설정 여부를 표시하며 프로세스 상태를 직접 검증하지 않는다고 명시한다. 별도의 Compose 목록에서 scheduler 프로세스가 실행 중인 것은 확인했지만, **미래의 각 예약이 기한대로 실행된다는 보장은 아니다.**

마이그레이션은 `001_kernel`부터 `021_text_work_links`까지 적용되어 있었다. `022_text_work_joins`는 현재 미커밋 코드에만 있으며 이 로컬 DB에는 적용되지 않았다. 이 확인을 위해 사용자 DB에 테스트 업무를 만들거나 기존 데이터를 삭제하지 않았다.

### 4.2 활성 Task와 Job

| Task | 활성 버전 | Job 유형 | 일정·상태 |
|---|---:|---|---|
| TASK-001 금융시장 브리핑 | 2 | CRON | `0 8 * * 1-5`, 활성 |
| TASK-002 규정 변경 영향 | 2 | EVENT | 문서 변경 이벤트, 활성 |
| TASK-003 VOC 개선 추천 | 4 | CRON | `0 9 * * 1`, 활성 |

일정은 서울 시간 기준이다. 조회된 다음 커서는 각각 2026-11-02 08:00, 09:00 서울 시간이다. 커서와 실행 중인 프로세스는 예약 설정이 존재한다는 근거이지 특정 시각의 성공 실행을 증명하지 않는다. Cron은 한국 공휴일을 따로 판별하지 않는다.

현재 로컬 DB에는 사용자 업무 설계 **0개**, 텍스트 개선 실험 **0개**, 단일 텍스트 업무 연결 **0개**가 있었다. 따라서 자연어로 만든 사용자 업무나 연결 업무의 기능은 격리 테스트·이전 시연으로 확인했지만, 현재 로컬 DB에서 사용자의 실제 업무가 이미 지속 운영 중이라는 증거는 없다.

### 4.3 Work와 Run 이력

| Task | Work 상태별 개수 | Run 상태별 개수 |
|---|---|---|
| TASK-001 | COMMITTED 6, REWORK_REQUIRED 1 | SUCCEEDED 6, VERIFICATION_FAILED 1, FAILED 1 |
| TASK-002 | COMMITTED 4, REWORK_REQUIRED 1, WAITING_APPROVAL 1 | SUCCEEDED 5, FAILED 1 |
| TASK-003 | COMMITTED 5 | SUCCEEDED 5 |
| 합계 | **18 Work** | **19 Run** |

Work와 Run의 개수가 다른 것은 정상이다. 하나의 Work에 여러 시도가 있을 수 있고, 사람 검토 대기 Work에는 자동 Run이 없을 수 있다. 과거 실패가 남은 것은 이력 보존의 증거다. 이 작은 데모 이력만으로 성공률·장애율이나 운영 신뢰성을 추정할 수는 없다.

TASK-002의 `COMMITTED 4`는 서로 다른 규정 변경 4건을 뜻하지 않는다. 루트 분석 Work 1개와 후속 Work 3개다. 나머지는 루트 실패 이력 1개와 후속 사람 검토 대기 1개다. 또한 현 DB에서 `work.created` 이벤트의 actor는 `user` 또는 `webhook`으로 기록되어 있어 이 집계만으로 실제 스케줄러가 발화한 실행 횟수를 구분할 수 없다.

TASK-001의 성공 Run 6개 중 3개는 `MOCK`, 3개는 모델 ID `gpt-6-luna`였다. TASK-002/003 Run은 MOCK이었다. Artifact는 총 17개, Work 의존성은 4개였다. Artifact 총수는 실패한 검증의 보존 기록을 포함할 수 있으므로 17개가 모두 채택된 성공 산출물이라는 뜻이 아니다. 이 수치는 샘플 작업·과거 시행을 포함한 현재 DB 집계이며, 처리한 실제 고객 건수나 개선 효과가 아니다.

같은 시점에 정책 API는 가상 `POLICY-VOC` v1/v2와 최신 변경 이벤트가 존재하며, TASK-003의 문서 의존성은 v1에 고정된 `REVIEW_REQUIRED`라고 반환했다. Work 큐의 기록 17건은 모두 `DONE`이었다. `DONE`은 큐 항목의 처리 상태이지 해당 업무가 모두 성공하거나 사람 검토가 완료됐다는 뜻은 아니다.

### 4.4 저장된 평가와 주의할 점

| Task | 현재 저장된 Evaluation 집계 |
|---|---|
| TASK-001 | `market-suite-v1`: PASS 3·FAIL 1, `v2`: PASS 1, `v3`: PASS 2 |
| TASK-002 | `policy-suite-v1` PASS 1, `v2` PASS 1, 후속 검증·인덱스·VOC 회귀 각각 PASS 1 |
| TASK-003 | `voc-run-suite-v1` PASS 5 |

서로 다른 평가셋 버전은 검사 범위가 같다고 가정할 수 없다. 특히 실패와 통과 개수를 단순 합산하거나 오래된 PASS를 최신 검증의 통과로 바꾸어 해석하면 안 된다.

개선안은 총 6개로 `ROLLED_BACK` 2개, `REJECTED` 3개, `PROPOSED` 1개였다. 활성 VOC 방법은 `champion-v1`, 상태 버전 5였다. 남은 `PROPOSED/PASS` 1개는 **`voc-classifier-eval-v1` 결과**이며 별도 회귀셋 결과가 없다. 현재 구현은 `voc-classifier-eval-v2`와 현재 회귀셋 해시를 적용 전에 요구하므로, 과거 PASS만으로 현재 기준의 적용 가능성을 주장할 수 없다. 이전 기록 중 별도 회귀셋이 없는 값은 0건 통과가 아니라 **미기록**이다.

| 출처 오류와 복구 | 출처 하나 누락 후 같은 Work 재시도 | 첫 Run `VERIFICATION_FAILED`, 새 Run 성공, 두 시도 보존 | 실패를 감추지 않고 복구하는 흐름 |
| 실제 모델 | 가상 입력으로 LIVE LLM 실행 | 현 DB에서 `gpt-6-luna` 성공 Run 3개 | 모델 호출의 실재성. 금융 해석의 의미 검증은 아님 |
| 출처 연계 | 로컬 PostgreSQL·OpenSearch와 원천 해시 | 쿼리·검색 참조·Evidence 기록 | 로컬 합성 문서와 데이터에 대한 출처 추적 |

현재 테스트의 구체적인 검증은 [test_market.py](../tests/test_market.py)와 [test_search.py](../tests/test_search.py)에 있다. 이전 분리 환경의 실제 HTTP/worker 시연 이력은 [WORK_STATE.md](WORK_STATE.md)에 기록되어 있다.

**해석:** 보고서 버전과 검증 실패/복구를 보여 준다는 점에서 목표에 맞는 기능적 성과가 있다. 30의 차이는 미리 정해진 가상 값의 차이이며 예측력이나 금융 분석 품질의 개선이 아니다. 모델 문장의 사실성·논리·실제 의사결정 가치는 `NOT_VERIFIED`다.

### 5.2 TASK-002 — 정책 변경과 영향 DAG

**목표:** 문서 변경을 단일 답변이 아니라 영향받는 업무와 후속 Work의 연결로 추적한다.

| 확인 항목 | 테스트 입력·동작 | 기대·관찰 결과 | 근거 범위 |
|---|---|---|---|
| 변경 이벤트 | 가상 `POLICY-VOC` v1 → v2와 양쪽 해시 | 변경 조항, 출처와 영향 대상 기록 | 가상 문서의 결정론적 차이 |
| 중복·동시 전달 | 같은 이벤트를 6개 동시 요청하고 다시 전달 | 하나의 루트 Work만 생성 | 시험한 동시성 조건에서의 멱등성 |
| 전파 | 영향을 받는 기존 Work와 연결 Task | 기존 Work `STALE`, 관련 Task `REVIEW_REQUIRED` | 의존성 변경 감지와 상태 표시 |
| 후속 Work | 분석 재검사 → 로컬 인덱스 → VOC 고정 사례 검사 → 사람 검토 | 앞선 검사 통과 후 담당자 검토 대기/기록 | 네 단계의 Work DAG와 검사 결과 |
| 변조·재시도 | 조항 차이나 재검사 영수증 위조 | 검사 실패·후속 단계 차단, 재시도 시 새 Run | 검증 실패가 곧 승인되지 않는다는 근거 |

구체적인 동시성·위조 검사는 [test_policy.py](../tests/test_policy.py), 검색 인덱스는 [test_policy_index.py](../tests/test_policy_index.py), 변경 중 회귀 검사는 [test_policy_regression.py](../tests/test_policy_regression.py)에서 확인한다. [e2e_stack.py](../tests/e2e_stack.py)는 별도 환경에서 HTTP API와 워커를 이용한 전체 시나리오다. 이전 실행 기록에 세 검사 완료 후 사람 검토를 기록하되 실제 정책 적용은 하지 않은 것으로 남아 있다.

**해석:** 문서 변경이 지속 Work와 의존성·검토로 전파된다는 점에서 핵심 제품 목표를 직접 보여 준다. 다만 문서 내용의 법적 해석이나 운영 규칙의 자동 적용을 증명하지 않는다. 로컬 인덱스 갱신은 가상 문서에 한정된다. VOC 회귀 검사는 분류 규칙의 합성 사례 결과를 검사하며 정책 변경의 실제 영향이나 인과관계를 판정하지 않는다.

### 5.3 TASK-003 — VOC 피드백과 개선 평가

**목표:** 단순히 새 보고서를 생성하는 것과 같은 입력에서 업무 수행 방식을 개선하는 것을 구분하고, 평가 결과에 따라 사용자가 직접 적용·기각·롤백한다.

| 시험 대상 | 기본 합성 평가 24건 | 별도 합성 회귀 6건 | 결과와 의미 |
|---|---|---|---|
| `champion-v1` | 18/24, 75% | 3/6 | 가상 기준 방법 |
| `challenger-v2` | 24/24, 100%, 기존 대비 개선 6·퇴행 0 | 6/6, 퇴행 0 | 최신 테스트 정의에서 PASS 가능한 후보. +25%p는 이 합성 분류셋의 수치 |
| `challenger-regressed` | 17/24, 퇴행 3 | 테스트에서 별도 회귀도 발생 | FAIL·적용 거부·기각 경로 |
| `challenger-overfit` | 24/24, 기본셋 퇴행 0 | 별도셋 퇴행 2 | 기본셋만 좋더라도 FAIL로 차단 |

이 수치는 [test_voc.py](../tests/test_voc.py)의 고정 사례와 사전 정의된 분류 방법에서 나온다. 24건과 6건은 소스에 포함된 합성 사례이며 독립적으로 수집한 미공개 실제 고객 표본이 아니다. 따라서 **분류 규칙의 데모 정확도 차이**이며 모델의 일반적 성능, 고객 만족도 또는 비용 절감의 증거가 아니다.

테스트는 후보 적용 전 자동 변경 금지, 같은 평가 입력, 사례별 퇴행, 평가셋/원천/현행 방법 변경 시 오래된 제안 적용 차단, 적용 후 다음 Run, 기각과 롤백을 확인한다. 현 로컬 DB에 실제로 남은 6개 개선안의 상태와 평가기 버전은 제4.4절과 같다. 특히 과거 `v1` PASS에 없는 별도 회귀셋 기록을 최신 `v2` 통과로 소급하면 안 된다.

## 6. 자연어 업무 등록부터 피드백까지

### 6.1 등록과 시각 검토

1. 사용자가 설명을 입력하면 `MOCK` 고정 초안 또는 `LIVE_LLM` 구조화 초안을 생성한다. LIVE 설명과 피드백은 모델 서비스로 전송된다.
2. 초안은 이름, 목표, 기대 결과, 평가 기준, 단계 ID·목적·선행 ID, 확인 질문을 담는다. 단계는 1~12개, 평가는 1~12개로 제한하고 순환·없는 선행 단계 등을 거부한다.
3. 사용자가 단계와 기준을 직접 수정하거나 자연어 변경 요청을 보낸 뒤 새 초안 버전으로 저장한다. 저장하지 않은 직접 수정이 있을 때 자연어 요청을 막아 덮어쓰기를 피한다.
4. 사람이 검토한 구조와 입력 텍스트, MOCK/LIVE 모드, 선택적인 Cron을 지정해 `TaskDefinition`과 `JobDefinition`을 등록한다.
5. 실행 시 해당 Work의 계약과 텍스트 입력 버전을 고정한다. 각 단계는 순서와 의존 단계의 결과를 사용한다. 구조 검사를 통과해도 의미 검토는 수행하지 않으며 `WAITING_APPROVAL`로 남는다.

화면은 단계별 카드와 선행 ID를 보여 준다. 노드-간선 편집기로 복잡한 모든 Work DAG를 자유롭게 구성한다고 표현하기는 어렵다. 입력은 직접 제공한 텍스트와 선택적인 선행 업무 결과이며, 새 업무마다 임의 외부 DB·API·파일·도구에 자동 접근하는 기능은 아니다. 근거: [WorkDesignStudio.vue](../frontend/src/WorkDesignStudio.vue), [text_sources.py](../backend/app/workloads/text_sources.py), [text_workflow.py](../backend/app/workloads/text_workflow.py).

### 6.2 결과에 대한 사람의 피드백

사용자는 결과를 채택하거나 보완 요청하고 이유를 기록할 수 있다. 사람이 작성한 비식별 평가 입력, 기대 동작과 필수·금지 문구를 고정 사례로 보관해 기존·후보 구조에 같은 입력을 재실행할 수 있다. 원문에 포함된 모든 개인정보를 자동 탐지하는 기능은 아니며, 사용자가 평가 데이터를 비식별화해야 한다.

방법 개선 비교는 유효한 양쪽 실행, 같은 실제 모델, 퇴행 없음, 최소 한 사례 개선 등 조건을 확인하고, 이후 사람의 명시적 `APPLY` 또는 `REJECT`를 요구한다. 적용 후에는 기존 버전으로 롤백할 수 있다. 기대 결과나 평가 기준의 추가는 별도 변경 종류로 분리한다. 기존 목표나 기준의 수정·삭제는 사람의 사유와 확인을 받아 **계약 변경**으로 적용·복구하며, 이 자체를 방법 성능 향상이라고 부르지 않는다. 근거: [text_regression.py](../backend/app/evaluation/text_regression.py), [text_experiments.py](../backend/app/evaluation/text_experiments.py), [text_decisions.py](../backend/app/evaluation/text_decisions.py), [text_contract_changes.py](../backend/app/evaluation/text_contract_changes.py).

**핵심 한계:** 텍스트 고정 사례의 자동 점수는 필수/금지 문구의 포함 여부다. 특정 문구가 들어간 결과가 올바르거나 유용하다는 뜻은 아니다. [이전 실제 모델 비교 기록](WORK_STATE.md)은 가상 배송 문의 1건에서 기존 1/1, 후보 1/1 동점으로 FAIL이며 의미 품질은 `NOT_EVALUATED`였다. 이것은 **실제 품질 향상 입증이 아니라 오히려 개선을 주장할 근거가 없었던 사례**다.

## 7. 지속 실행·DAG·출처의 구현 수준

### 7.1 Work와 Run의 분리

`TaskDefinition`은 버전이 있는 업무 계약, `JobDefinition`은 수동·예약·이벤트 실행 정책, `WorkItem`은 지속되는 작업, `Run`은 한 번의 시도다. 공식 상태·이벤트·큐·Evidence는 PostgreSQL이 소유한다. 실패하거나 lease가 만료되면 실패 시도를 남기고 같은 Work에 새 Run을 만든다. Redis Streams는 알림 경로이고 PostgreSQL 큐가 복구 기준이다. [service.py](../backend/app/work/service.py), [scheduler.py](../backend/app/scheduler.py), [worker.py](../backend/app/worker.py), [001_kernel.sql](../backend/migrations/001_kernel.sql)을 참고한다.

`LangGraph` 데모는 `inspect_context → draft → finalize`와 PostgreSQL 체크포인트를 사용한다. [test_graph_runtime.py](../tests/test_graph_runtime.py)는 lease가 살아 있는 동일 Run을 새 Python 프로세스에서 **명시적으로** 재개하고 완료된 단계를 반복하지 않는 것을 확인한다. 반면 lease가 만료된 장애 Run을 자동으로 같은 Run에서 이어받는 것은 아니며 새 Run을 만든다. 자연어 텍스트 단계 실행도 이 데모 그래프와 별도 경로다.

### 7.2 현재 반영된 단일 선행 연결

사용자가 텍스트 업무 A → B를 설정하면 A 결과의 사람이 기록한 `ACCEPT`에 따라 B Work가 생긴다. B의 당시 입력 버전과 A의 Work·Artifact ID·해시를 고정하고, A가 오래되면 B의 검토 대기·완료 상태에도 영향이 전파된다. 단일 연결을 중지해도 이미 생성된 작업은 유지된다. 대상의 Cron 중지와 이 연결 중지는 별개다.

이전 격리 실험에서 `문의 분류 → 개선 방안`의 화면 연결, 후속 MOCK 작업, 선행 해시와 검토 대기를 확인했다. 같은 기록에는 합성 MOCK 선행 결과가 실제 `gpt-6-luna` 후속 입력에 포함되고 후속 Run이 `SUCCEEDED · WAITING_APPROVAL`로 남은 사례도 있다. 이는 연결과 모델 호출의 증거이며 후속 답변이 좋은지 검증한 것은 아니다. 선행 MOCK 결과를 LIVE 모델이 사용해도 선행 데이터가 실데이터로 바뀌지 않는다.

### 7.3 여러 선행 결과 결합: 미커밋·미배포

현재 작업 트리에는 선행 텍스트 업무 2~8개의 새 채택 결과를 모으는 진행 중 코드와 UI가 있다. 마지막 결합 이후 각 업무의 최신 새 결과가 모두 준비되면 하나의 후속 Work를 생성하고, 순환·중복·STALE을 다루는 방향이다. 관련 코드: [text_joins.py](../backend/app/workloads/text_joins.py), [022_text_work_joins.sql](../backend/migrations/022_text_work_joins.sql), [TextWorkJoins.vue](../frontend/src/TextWorkJoins.vue), [test_text_work_joins.py](../tests/test_text_work_joins.py).

**보고서 조사 시점의 구현 기준 커밋 `92ed5ac`에는 이 코드가 포함되지 않고 로컬 `workos-p0`에도 적용되지 않았다.** 별도 테스트 결과는 제10절에 적는다. 결합 규칙은 ‘각 소스에서 마지막 결합 후 도착한 최신 결과’이며 같은 사건·기간·고객에 대한 결과인지 자동으로 보증하지 않는다. 범용 상관관계 키, 입력 지연 정책과 사용자 업무별 의미적 정합성은 후속 설계가 필요하다.

## 8. ‘100개 업무에도 Kernel 거의 수정 없음’ 구조 평가

### 8.1 개선된 점

- [registry.py](../backend/app/workloads/registry.py)에 Task별 또는 종류별 실행기, 검증기, 검증기 선택, 트리거·채택 후처리, 재시도·재검증·검토 guard 등록점이 있다.
- 세 데모의 실행·검증 및 정책·금융·VOC 컨텍스트 처리가 업무 모듈로 이동했다. 공통 `Kernel`에 `TASK-001/002/003` 분기를 계속 추가하는 방식은 줄었다.
- `provided_text_workflow_v1`은 서로 다른 텍스트 업무가 하나의 종류별 실행기와 검증 경로를 공유한다. 단일 선행 연결도 업무 ID를 하드코딩하지 않고 설정으로 구성한다.
- [example_total.py](../backend/app/workloads/example_total.py)는 다른 종류의 결정론적 계산 업무를 신뢰된 확장 모듈로 등록하는 예다. [test_workload_extension.py](../tests/test_workload_extension.py)는 확장 실행·검증·변조 거부 등을 확인한다.
- [test_registered_work.py](../tests/test_registered_work.py)의 100건 검사는 10개 이름 범주, 다른 목표와 1~3단계 구조를 이용해 동일 텍스트 실행기와 사람 검토 게이트를 반복 사용한다. 해당 테스트에서 대시보드의 읽기 쿼리는 2회다.

### 8.2 아직 부족한 점

1. **100개 테스트의 다양성은 계약 텍스트와 단계 구성 수준이다.** 100개의 서로 다른 API, 문서 형식, 권한, 평가 방식, 장기 실행이나 외부 도구를 처리한 것이 아니다. MOCK은 실제 분석 결과도 만들지 않는다.
2. 새로운 업무 종류가 공통 텍스트 모델에 맞지 않으면 실행기·독립 검증기·Task/Job 등록, 배포 설정, 경우에 따라 UI 및 테스트가 필요하다. 신뢰된 Python 확장은 샌드박스가 아니다.
3. 세 데모용 [GraphRunner](../backend/app/runtime/graph.py)는 여전히 `TASK-001/002/003`에 대한 컨텍스트·보고서 계약 분기를 포함한다. 이를 Kernel에서 업무별 코드를 분리한 성과와 별개로 보아야 한다.
4. 자연어 설계가 필요한 도구·연결·권한을 실행 가능한 안전한 커넥터 정의로 일반 변환하지 않는다. 임의 외부 API 실행, 파일 수집, 실제 고객 시스템 변경은 지원하지 않는다.
5. 서로 다른 Task 종류, 다중 선행 조건, 이벤트 종류, 실패 보상과 사용자별 평가 기준을 선언만으로 구성하는 범용 프레임워크는 미완성이다. 다중 텍스트 결합은 현재 미커밋이다.
6. 업무가 많아질 때 동시 처리량·대기 시간·DB 부하·장애 격리·비용은 부하 시험하지 않았다. 대시보드 쿼리 수가 2회라는 사실만으로 100개 업무의 운영 확장성을 결론낼 수 없다.

**판정:** ‘공통 Kernel을 업무별 분기로 늘리지 않는 방향’과 ‘동형 텍스트 업무를 데이터로 등록하는 경로’는 입증되었다. ‘서로 다른 100개 실무를 Kernel 수정 없이 추가한다’는 더 강한 목표는 **아직 입증되지 않았다**.

## 9. 결과가 실제 목표에 가까워졌는가

| 질문 | 현재 답변 | 판단 이유 |
|---|---|---|
| 단발성 채팅이 아니라 업무를 등록한 것처럼 보이는가? | **부분적으로 예** | 설계·Task/Job·입력 버전·반복 실행과 이력이 있다. 다만 실제 사용자 업무 등록은 현 DB 0건이다. |
| 같은 업무의 실행 결과와 변화를 볼 수 있는가? | **예, 구현 범위 내** | 실행 이력, 금융 버전 수치 비교와 검증 상세가 있다. 검사 버전이 다르면 점수 비교에 주의해야 한다. |
| 문서 변경이 후속 업무를 만드는가? | **합성 데모에서는 예** | 가상 문서 이벤트가 영향과 네 후속 Work를 생성한다. 외부 문서 시스템 일반 연동은 아니다. |
| 결과를 신뢰할 근거를 볼 수 있는가? | **일부 예** | 출처 ID·해시, 구조·수치 Evidence, 사람 검토가 있다. 자연어 의미와 실제 사실은 별도다. |
| 실패·피드백이 다음 수행 방식 개선으로 이어지는가? | **고정 사례 데모에서는 예** | VOC 비교와 텍스트 고정 사례 경로가 있다. 실제 업무에서 생산성·정확성이 향상됐는지는 미측정이다. |
| 적용하지 않거나 이전 버전으로 돌릴 수 있는가? | **구현·테스트됨** | 평가 통과 후 명시적 적용, 기각과 롤백 경로가 있다. 사용자 계약 변경은 별도 이력으로 다룬다. |

현재 가장 확실한 성과는 **이력·근거를 가진 지속 업무와 사람 통제의 기술적 연결**이다. 가장 큰 미확인 사항은 **실제 업무의 결과 품질과 생산성 향상**이다. 이 둘을 같은 주장으로 묶지 않는 것이 다음 검증의 출발점이다.

## 10. 테스트 및 검증 내역

### 10.1 이번 보고서 작성 중 확인

- 실제 `workos-p0`에 대해서는 Compose 상태, health, UI HTTP 응답, 활성 Task/Job, Work·Run·Evaluation·개선안의 **읽기 전용 집계**를 확인했다. 사용자 DB를 테스트로 초기화하지 않았다.
- 현재 작업 트리 `pytest --collect-only -q tests`: **108개 수집**. 수집은 실행 성공을 뜻하지 않는다.
- 전용 PostgreSQL에서 `tests/test_text_work_joins.py tests/test_text_work_links.py tests/test_review_dependency.py tests/test_workload_extension.py`: **20 passed, warning 1건**. 일시 중지 직전 추가된 출처 소유 Work 확인 코드까지 포함한 실행이다. 프런트엔드 전체 상호작용이나 실제 LLM 의미 품질 검사는 아니다.
- 현재 작업 트리에서 `tests/test_market.py tests/test_policy.py tests/test_policy_index.py tests/test_policy_regression.py tests/test_voc.py tests/test_voc_history.py tests/test_voc_sources.py tests/test_graph_runtime.py tests/test_scheduler.py tests/test_redis.py tests/test_registered_work.py`를 전용 PostgreSQL·Redis와 임시 OpenSearch 인덱스로 실행: **33 passed, warning 1건, 245.08초**. 이 중 100개 업무 검사는 같은 텍스트 실행기의 가상 사례다.
- 동일 작업 트리에서 `python -m pytest -x -q tests` 전체 실행: **108 passed, warning 1건, 421.04초**. 전용 PostgreSQL·Redis와 로컬 OpenSearch의 고유한 임시 인덱스를 사용했으며, 미커밋 결합 코드도 포함했다. 이는 현재 작업 트리에서의 자동 테스트 결과이고 `workos-p0`에 022가 적용되었다는 뜻은 아니다.
- 이번 보고서에서 `tests/live_llm_smoke.py`나 `tests/e2e_stack.py`를 실행 중인 사용자 프로젝트에 호출하지 않았다. 두 스크립트는 명시적으로 격리 환경을 요구하며 LIVE 스모크는 유료 호출이다. 이전의 격리 환경 관찰은 [WORK_STATE.md](WORK_STATE.md)의 해당 시점 기록이다.

### 10.2 이전 전체 회귀와 읽는 방법

단일 텍스트 업무 연결을 반영한 이전 커밋 시점에는 PostgreSQL·Redis·임시 OpenSearch 인덱스를 사용한 전체 회귀 **101 passed, warning 1건**이 기록되어 있다. 그 전체 테스트를 시작한 뒤 작성된 일부 연쇄·기각·lease 복구 검사는 별도로 실행되었다. 이번 작업 트리에는 미커밋 결합 테스트가 추가되어 있으므로, 101과 현재 수집 개수 108을 같은 코드 스냅샷의 결과로 해석해서는 안 된다.

테스트가 확인하는 주요 불변식은 다음과 같다.

- **상태·실패:** 허용되지 않은 전이 거부, 중복 요청, 동시 claim, lease 만료, 실패 Run 보존, 기존 정상 Artifact 보존.
- **의존성:** Work DAG 순환 거부, 선행 완료 전 실행 차단, 선행 변경에 따른 STALE, 검토 직전 낡은 근거 차단.
- **출처:** 해시·수치 변조, 누락 문서, 읽기 전용 SQL 권한, 검색 문서 변경과 복구.
- **개선:** 같은 사례 재실행, 퇴행 차단, 최신 평가/방법/원천 확인, 명시적 적용·기각·롤백.
- **확장·규모:** 신뢰된 등록형 실행기, 여러 텍스트 계약 공유 실행, 100개 가상 텍스트 업무와 목록 조회.
- **진행 중 결합:** 새 결과 대기, 최신 도착 선택, 순환 거부, 중지 후 재개, 오래된 근거와 변조 차단. 테스트 범위는 현재 작성된 사례에 한정한다.

테스트의 PASS는 코드가 해당 조건에서 기대한 결과를 냈다는 뜻이다. 실제 외부 시스템의 보안, 모든 장애 유형, 의미적 품질, 운영 수준의 성능이나 사용자 만족도를 인증하지 않는다.

## 11. 주요 위험과 해결 우선순위

| 우선 | 관찰된 간극 | 사용자 목표에 미치는 영향 | 필요한 다음 검증 |
|---:|---|---|---|
| 1 | 실제 사용자 업무·데이터·인간 평가 0건 | 실제 업무 수행 능력과 가치가 입증되지 않음 | 비민감한 실제 업무 1~2개 선정, 기준선과 사람 평가, 시간·오류·재작업 측정 |
| 2 | 의미 평가는 대부분 사람 판단 또는 문자열 검사 | 형식 PASS가 정답·유용성으로 오인될 수 있음 | 사람 라벨 고정 사례, 근거 충실도·누락·유용성 평가, 모델 평가 시 사람과의 일치도 기록 |
| 3 | 도구·원천 유형이 텍스트/합성 데모 중심 | 도메인이 달라지면 모듈과 검증기 개발이 필요 | 읽기 전용 커넥터 계약과 권한·스냅샷, 서로 다른 최소 3종 업무로 확장 시험 |
| 4 | 다중 선행 결합은 미커밋 | 여러 입력을 합친 지속 업무를 현재 서비스에서 쓸 수 없음 | 코드 검토, 결합 상관관계·지연·중복·복구 정책, UI와 실제 모델 경로 검증 후 적용 |
| 5 | 100개 검사가 동형 MOCK이고 부하 수치는 없음 | 규모·다양성 목표를 과대평가할 위험 | 비슷하지 않은 작업군과 10/100개 등록, Kernel 변경량·처리량·대기 시간·비용을 별도 측정 |
| 6 | 운영 보안·관측·자동 복구 미성숙 | 실제 서비스로 사용하기 어려움 | 배포 경계·비밀 관리·권한·감사, 복구 훈련과 SLO 정의 |
| 7 | 안내 문서 일부가 최신 기능과 어긋남 | 사용자가 가능한 기능을 찾지 못할 수 있음 | [DEMO.md](DEMO.md)의 텍스트 비교·승격 미지원 문구를 현 코드와 맞게 갱신 |
| 8 | 비밀 주입 설명과 실제 Compose 설정이 다름 | 모델 키가 어느 프로세스에 제공되는지 잘못 이해할 수 있음 | [docker-compose.yml](../docker-compose.yml)과 README 설명을 일치시키고 운영용 비밀 주입 경계를 설계 |

특히 [DEMO.md](DEMO.md)의 ‘텍스트 후보 재실행·비교나 승격 미지원’ 설명은 현재 코드의 고정 사례 비교·명시적 적용 기능보다 오래된 내용이다. 반대로 화면의 `MOCK`과 `LIVE_LLM`, 의미 미검증 표시를 제거하면 안 된다. 이 보고서는 문서 불일치를 기록하며 안내 문서 자체를 수정하지 않았다.

또한 [README.md](../README.md)는 `.env.apikey`를 워커 환경에만 전달한다고 설명하지만, 현재 Compose의 `env_file`은 **API와 worker 모두**에 지정돼 있다. API의 LIVE 업무 설계·피드백 경로도 모델 호출을 사용한다. 이는 키 값 노출을 뜻하는 관찰은 아니지만, 실제 비밀의 프로세스 경계를 README대로 가정해서는 안 된다는 뜻이다. 이 보고서에는 키 값이나 사용자 입력 원문을 포함하지 않았다.

## 12. 다음 단계와 수락 기준 제안

1. **하나의 실제 업무를 안전한 파일럿으로 정의한다.** 입력 원천·접근 권한·기대 산출물·사람 검토자·실패 시 조치를 정한다. 기존 수작업 처리 시간과 오류/누락을 먼저 기록한다. 목표는 특정 자동화율 숫자를 미리 선언하는 것이 아니라 동일 기준으로 전후를 측정하는 것이다.
2. **고정 평가를 업무 의미에 맞게 만든다.** 사람이 라벨링한 정상·경계·오류·개인정보 포함 사례와 실패 비용을 정하고, 필수 문구 검사와 별도로 근거 충실도·누락·실제 유용성을 채점한다. LLM 평가를 쓰면 평가 기준·버전·불확실성과 사람 판정 일치도를 남긴다.
3. **서로 다른 업무 유형으로 확장성을 시험한다.** 예를 들어 문서 변경 검토, 정형 SQL 집계, 텍스트 분류처럼 출처와 검증 방식이 다른 업무를 각각 추가하고 변경 파일·Kernel 수정 여부·실패 및 복구를 기록한다. 그 후에 10개·100개로 늘려야 숫자가 의미 있다.
4. **결합과 이벤트 계약을 완성한다.** 여러 선행 결과의 상관관계 키, 새로움·유효기간, 늦게 도착한 데이터, 중복, 재시도와 부분 실패 정책을 사용자 화면과 Evidence에 노출한다. 미커밋 022는 완성 후 별도 마이그레이션·전 과정 검증이 필요하다.
5. **배포 가능성을 평가한다.** DB 백업·복구, 예약/워커 중단 훈련, 장애 알림, 보안·권한·데이터 보존, 동시 부하와 비용을 검증한다. 데모에서 확인된 내용과 운영 수용 기준을 분리한다.
