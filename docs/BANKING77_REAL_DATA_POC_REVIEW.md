# Work OS 공개 데이터 PoC — BANKING77 문의 분류 독립 검토 보고서

- 실행일: 2026-11-01 (Asia/Seoul)
- 검토 목적: 프로젝트 목표인 ‘사람이 하던 반복 업무의 개입을 줄이면서 품질을 높이는가’에 대해, 실제로 확인된 사실과 확인되지 않은 효과를 외부 검토자가 구분할 수 있게 한다.
- 판정: **공개 벤치마크에 대한 실제 Work OS + LLM 실행은 확인. 비교 분류기보다 품질 우위는 관찰되지 않음. 사람의 시간 절감과 현업 효과는 미입증.**

## 1. 왜 이전 데모보다 유효한가

기존 PoC의 24건과 정답은 이 저장소를 위해 작성된 합성 사례였다. 본 실험은 외부에서 공개한 [BANKING77 데이터셋](https://huggingface.co/datasets/PolyAI/banking77)의 공식 테스트 분할과 원래 라벨을 사용했다. 데이터셋은 은행 서비스 질의를 77개 의도로 분류하는 영어 벤치마크다. [원 논문](https://aclanthology.org/2020.nlp4convai-1.5/)은 13,083개 질의를 기술한다. 데이터셋 카드의 라이선스는 CC BY 4.0이며, 원 저자 Casanueva 등과 PolyAI-LDN에 출처를 밝힌다.

**정확한 표현:** 외부에서 공개된 은행 문의 벤치마크의 실제 레코드를 사용했다. 각 문장이 실제 은행 운영 중 발생한 고객 대화인지, 특정 기업의 최신 고객 분포를 대표하는지는 확인하지 못했다. 따라서 실제 조직의 운영 데이터나 현업 성과로 부르지 않는다. 공개 데이터는 모델 사전학습 등에 이미 노출됐을 가능성도 배제할 수 없다.

## 2. 사전에 정한 실험 조건

- 원본: [PolyAI-LDN 저장소의 고정 커밋 `57ec275d8078af65b7731c2a98be812d844a6d6b`](https://github.com/PolyAI-LDN/task-specific-datasets/tree/57ec275d8078af65b7731c2a98be812d844a6d6b/banking_data). `train.csv` SHA-256 `b06e26ac675513959a63135f11b94ea7786ed02da65db93a5650d8838cbc664b`, `test.csv` SHA-256 `d12d6e3bc4c3103966ae786dc435913c0c563dfa328f5a3646d0e62cfeeb474d`.
- 대상: 카드 도착, 배송 예상, 카드 연결, 결제 수수료, 미인식 결제, 환율, ATM 카드 회수, 결제 거절 8개 클래스. 공식 테스트 분할에서 각 5건씩 총 **40건**을 `workos-banking77-holdout-v1`과 헤더를 포함한 원본 CSV 레코드 순번(파일의 물리적 줄 번호가 아님)의 SHA-256 순서로 선택했다. 실행 결과를 본 뒤 사례를 선택하지 않았다. 클래스별 5건으로 균형을 맞춘 소규모 표본으로, 실제 문의 비율을 반영하지 않는다.
- 정답: 데이터셋의 `category` 라벨. 분류할 때 모델에 개별 정답은 넣지 않고 질의 ID·원문과 8개 선택지를 제공했다. 원본 학습 분할과 40건 사이에 대소문자를 무시한 완전 일치 문장은 0건이었다. 의미상 중복과 LLM의 사전학습 노출은 확인하지 못했다.
- 비교 방법 A: 공식 **학습 분할**에서 같은 8개 클래스의 1,140건으로 학습한 단어 1~2그램 TF-IDF + LinearSVC (`scikit-learn 1.7.2`). 이 비교기는 단순 키워드 규칙이 아니라 감독학습 분류기다.
- 방법 B: 기존 Work OS의 텍스트 업무를 등록하고, 동일 테스트 40건을 10건씩 네 입력 버전으로 고정해 각각 별도 WorkItem/Run을 실행했다. 실제 OpenAI `gpt-6-luna`를 `LIVE_LLM`으로 호출했고, 허용 선택지 외 정답 예시는 전달하지 않았다. 업무 설계는 MOCK 초안의 사람 작성 수정이며 자연어→LLM 구조 변환의 성능을 평가한 것이 아니다.
- 점수: 각 항목의 단일 예측을 원본 라벨과 정확히 비교. 형식 오류·누락·중복 응답은 그 사례의 오답으로 계산한다. Work OS의 내부 구조 검증 결과와 이 외부 정답 비교를 별도로 표시한다.

비교기는 1,140건의 라벨을 학습했지만 LLM 프롬프트에는 그 예시를 넣지 않았다. 두 방법은 정보량·학습 방식·실행 환경이 다르므로 **LLM 대 통계 모델의 제한된 업무 대안 비교**이지, Work OS 자체가 품질을 높였는지 분리해 증명하는 실험이 아니다.

## 3. 실제 실행 결과

| 항목 | TF-IDF + LinearSVC | Work OS + LIVE LLM |
|---|---:|---:|
| 동일한 테스트 문의 | 40건 | 40건 |
| 원본 라벨과 일치 | **38/40 (95.0%)** | **37/40 (92.5%)** |
| 불일치 | 2건 | 3건 |
| 형식상 응답 누락 | 0건 | 0건 |

Work OS 방식은 이 표본에서 **1건, 2.5%p 낮았다.** 쌍별로는 Work OS가 비교기의 오답을 고친 사례 1건, 비교기가 맞힌 것을 Work OS가 틀린 사례 2건이었다. 두 방식 모두 틀린 사례는 1건이었다. 40건은 작고 8개 클래스를 균등 추출했으므로 이를 모집단 전체의 우열이나 유의한 성능 차이로 일반화하지 않는다.

### 사례별 차이와 위험

- **Q01:** 내역을 알 수 없는 청구에 대해 데이터셋 정답은 결제 수수료다. 비교기는 미인식 결제, LLM은 수수료로 분류했다. LLM이 기준 라벨과 일치한 1건이다.
- **Q07:** 환전 뒤 예상보다 많이 청구됐다는 문의의 데이터셋 정답은 환율 문제다. 비교기는 정답이었지만 LLM은 수수료로 분류했다.
- **Q08:** 발송한 카드의 추적을 요청하는 문의의 데이터셋 정답은 카드 도착이다. 비교기는 정답이었지만 LLM은 배송 예상으로 분류했다.
- **Q04:** 카드 도착을 기다린다는 문의의 데이터셋 정답은 배송 예상인데 두 방식 모두 카드 도착으로 분류했다.

Q04와 Q08은 카드 도착과 배송 예상의 경계가 직관적으로 모호하다. 위 ‘정답’은 데이터셋 라벨과의 일치이며, 독립적인 도메인 전문가가 라벨이나 실제 처리 경로의 적절성을 재검토한 결과가 아니다. 라벨 오류나 복수 해석 가능성을 숨기지 않았다. 전체 문장, 라벨, 양쪽 예측과 응답은 [원시 증거](evidence/banking77/run.json)에 포함했다.

## 4. Work OS에서 실제 수행한 것과 증거

동일 Task의 소스 버전 네 개에 대해 각각 실제 WorkItem을 큐에 넣고 기존 `process_claim` 워커 경로로 실행했다. 네 Run의 모델 응답과 입력, 해시, 모델 ID, 응답 ID, 구조 검증 결과가 원시 증거에 남아 있다. 테스트는 별도 PostgreSQL `banking77_poc`에서 실행했으며 사용자 운영 DB에 실험 기록을 넣지 않았다.

네 건 모두 `provided-text-structure-v3`의 8개 구조·연결 검사를 통과했다. 이 검증기는 **분류 의미나 라벨 일치를 검증하지 않으며** 결과에 `semantic_review=NOT_PERFORMED`, `requires_human_review=true`를 기록했다. 따라서 성공적인 Run과 구조 검사 통과를 정확한 분류 또는 최종 업무 채택으로 해석하면 안 된다. 사람의 실제 승인도 하지 않았다.

이 실험에서 확인한 Work OS의 효과는 작업 계약과 4개 입력 버전, Work·Run·산출물·Evidence의 연결 및 검토 대기 상태를 남길 수 있다는 것이다. 개선 제안→동일 고정 평가→사용자 적용, 주간 예약, 재시도·DAG, 실제 운영 화면의 현업 사용은 이 실험에서 수행하거나 성과로 입증하지 않았다. LLM을 직접 호출하는 단발성 방식과의 정량 비교도 하지 않았다.

## 5. 시간·비용 및 인력 효과

- 네 LLM Work의 순차 실행 구간은 각각 **9,265ms, 4,093ms, 2,875ms, 2,672ms**, 합계 **18,905ms**였다. 이는 본 실행의 요청/처리 시간으로 사람의 검토 시간이나 End-to-End 업무시간이 아니다. 네트워크, 모델 부하, 묶음 크기에 영향을 받는다.
- LLM 사용량은 입력 **1,638 토큰**, 출력 **997 토큰**이다. 요금표·캐시·청구 상세를 검증하지 않았으므로 비용 금액은 계산하지 않았다.
- 비교 분류기의 현지 CPU 학습 기록은 31ms, 40건 추론은 밀리초 정수로 반올림해 0ms였다. 0ms가 무시간을 의미하지 않으며 서로 다른 방식과 환경을 사용한 단일 실행이다. 개발·라벨링·운영 비용은 포함하지 않는다.
- 사람의 직접 분류 시간, 검토 시간, 인건비, 처리 완료율은 **측정하지 않았다**. 따라서 ‘1시간이 몇 분이 됐다’, ‘몇 % 절감했다’, ‘사람보다 정확하다’는 결론은 낼 수 없다. 이전 합성 데모의 임의 120초/45초는 본 실험 결과가 아니다.

## 6. 증거 재검증 방법

- [실험 코드](../experiments/banking77/run.py): 소스 선택, 학습, Work OS Task 등록 및 실제 모델 실행. 재실행은 API 비용이 들고 비결정적인 새 결과가 나오며, 현재 증거 파일을 덮어쓴다. **이름이 `banking77_poc`인 격리 DB**와 별도 환경변수로 API 키·모델을 설정해야 한다.
- [저장된 실행 증거](evidence/banking77/run.json): 40개 입력·헤더를 포함한 원본 CSV 레코드 순번(파일의 물리적 줄 번호가 아님)·원본 정답·비교기와 LLM 예측, 4개 Work/Run·컨텍스트·Artifact/Evidence·응답·토큰 수. 파일 SHA-256: `c9b78722f010788f837f560b6e66e0b316b48ec741b5c910481b96cb173d2b2c`.
- [독립 재검증 코드](../experiments/banking77/verify.py): API 키와 LLM 호출 없이 원본 파일을 고정 커밋에서 다시 읽어 해시·표본 선정·비교 모델 재학습·Work OS 컨텍스트와 Artifact 해시·응답 파싱·점수를 확인한다. `python experiments/banking77/verify.py` 실행 결과 **38/40 대 37/40**을 확인했다. Python 3.10.0, scikit-learn 1.7.2에서 실행했다. 외부 네트워크와 해당 패키지가 필요하다.
- 이 파일과 해시는 변경 여부를 점검하는 근거이지만, 파일 자체가 서명된 외부 CI나 모델 제공자의 독립 인증 기록은 아니다. 응답 ID는 기록했으나 제공자 측 재조회 검증은 하지 않았다. 독립 재검증은 원본 소스·저장된 결과의 일관성을 확인하며 LLM을 다시 실행하지 않는다.

## 7. GPT 검토 시 확인할 쟁점

1. 8개 클래스를 균형 추출한 40건의 대표성과 의도 경계가 불명확한 원본 라벨의 적합성.
2. 학습 사례 1,140건을 가진 감독학습 분류기와 사례를 받지 않은 LLM 비교가 어떤 질문에 답하며 무엇을 통제하지 못하는지.
3. Work OS 구조 검증과 독립 라벨 평가, 사람 승인, 실제 고객 대응 품질을 혼동하지 않았는지.
4. 현재 결과(37/40 대 38/40)에서 어떤 성능·비용·인력효과 주장이 가능한지, 과장된 해석은 없는지.
5. 현업 입증에 필요한 사전 등록된 비교 설계: 실제 반복 업무와 독립 라벨, 동일 범위의 사람 기준선, 준비·검토·수정·예외처리 시간, 품질·오류 심각도, 표본 크기·기간, 실제 새 주차 입력, 중단·실패와 비용.

## 8. 현재 결론과 다음 단계

공개 데이터에 대한 실제 LLM 수행, 버전 고정과 추적 가능한 기록은 관찰했다. 그러나 이 표본에서 Work OS + LLM은 더 단순한 감독학습 비교기보다 정확하지 않았고 사람의 시간 절감도 측정되지 않았다. 업무의 지속 개선이나 현업 ROI를 증명했다고 보고할 수 없다.

다음은 실제 사용자와 업무·평가 기준을 정해 사람이 직접 처리한 기준선을 측정하고, 독립적으로 확인된 새 입력에 대해 Work OS 사용 후의 총 사람 개입과 품질을 같은 방식으로 기록하는 것이다. 개선 후보가 있다면 개발용과 최종 검증용 데이터를 미리 분리하고 후보 적용 전후를 동일 고정 입력으로 평가해야 한다.
