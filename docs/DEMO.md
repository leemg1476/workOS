# Work OS 3분 데모

모든 시장 지표·규정·VOC와 평가 사례는 **가상 데이터**다. TASK-001에서 `LIVE LLM`을 선택하면 해석 문장만 실제 모델이 생성한다. 이 경우에도 출처 자료는 가상이며 모델의 해석은 의미적 정확성을 검증하지 않는다. TASK-002/003은 결정론적 MOCK이다.

## 준비

```powershell
docker compose -p workos-p0 up --build -d
```

[대시보드](http://localhost:5173)를 열고 상단 검색 상태가 `OPENSEARCH · connected`인지 확인한다. 처음 기동할 때 검색 인덱스 준비에 잠시 걸릴 수 있다. API 문서는 [localhost:8000/docs](http://localhost:8000/docs)에 있다.

이미 처리된 정책 변경은 중복 생성을 막기 위해 기존 작업을 다시 보여준다. **기존 데이터를 지우거나 실행 중인 프로젝트를 멈추지 않고** 새로운 시연 상태가 필요하면 새 PowerShell에서 별도 포트와 프로젝트를 사용한다. 프로젝트마다 DB 볼륨이 분리된다.

```powershell
$demoProject = 'workos-demo-' + (Get-Date -Format yyyyMMddHHmmss)
$env:WORKOS_POSTGRES_PORT='18543'
$env:WORKOS_REDIS_PORT='18679'
$env:WORKOS_OPENSEARCH_PORT='18920'
$env:WORKOS_UI_PORT='18517'
$env:WORKOS_API_PORT='18800'
docker compose -p $demoProject up --build -d
# http://localhost:18517 에서 시연한다.
# 종료 시 새 프로젝트의 볼륨과 기존 프로젝트 데이터는 유지된다.
docker compose -p $demoProject down
```

위 포트가 이미 사용 중이면 다른 빈 포트로 바꾼다. 이 PowerShell을 닫으면 해당 창에서 설정한 포트 환경변수도 사라진다. 별도 환경에서 자동 API/워커 E2E를 실행하려면 새 프로젝트를 띄운 **직후** 아래를 실행한다. 검증이 시연 상태를 진행시키므로, 초기 상태의 대화형 시연은 또 다른 새 프로젝트에서 시작한다.

```powershell
$env:WORKOS_E2E_CONFIRM='disposable'
$env:WORKOS_E2E_BASE='http://localhost:18800/api'
python tests/e2e_stack.py
```

대시보드 상단 `무엇이 달라졌나요?`에서 업무별 실행 이력과 검증 통과 결과 두 개를 선택해 비교할 수 있다. VOC 탭에는 합성 고정 평가의 개선·퇴행 요약도 표시된다. 실행 상세를 누르면 선택한 시도의 결과와 근거가 열린다.

## 1. TASK-001: 반복 실행과 검증

1. 데이터 `v1`, 해석 `MOCK`으로 실행하고 수치·출처 Evidence를 확인한다. `v2`로 한 번 더 실행한다.
2. `최근 결과 비교`에서 두 보고서를 선택하면 가상 USD/KRW `1,350 → 1,380`, 차이 `30`이 나온다.
3. `첫 시도에 출처 누락 테스트`를 선택하고 실행하면 `VERIFICATION_FAILED`다. 이력의 `같은 작업 재시도`로 새 Run이 생성되고 검증 통과 시에만 발행된다. 실패한 이전 시도는 유지된다.
4. 선택 사항: `.env.apikey`를 설정한 경우 `LIVE LLM`으로 실행할 수 있다. 보고서에 `LIVE_LLM`, `DEMO DATA`, 검색 모드, 검증기와 의미 미검증 해석이 각각 표시된다.
5. `이력 보기`에서 최근 Run의 `inspect_context`, `draft`, `finalize` 단계와 성공·실패 기록을 확인한다. 단계 완료와 산출물 검증 통과는 별개다. 기존 Run에는 단계 기록이 없을 수 있다.

## 2. TASK-002: 문서 변경과 후속 Work

1. `규정과 영향 보기`에서 가상 `POLICY-VOC` v1/v2와 TASK-003의 문서 의존성을 확인한다.
2. `변경 이벤트 발생` 후 보관기간 `90일 → 30일`, 검토주기 `매월 → 매주`, 조항 출처와 TASK-003의 `REVIEW_REQUIRED`를 확인한다.
3. 네 개의 연결된 후속 Work가 나타난다. 첫 작업은 원래 분석의 입력·해시·Evidence를 재검사하고, 두 번째는 가상 정책 v2를 로컬 OpenSearch에 추가한 뒤 버전·해시와 기존 v1 보존을 확인한다. 세 번째는 고정 VOC 사례 24건과 별도 사례 6건에서 현재 분류 방법이 `champion-v1` 기준보다 퇴행했는지 검사한다. 세 검사를 통과하면 각각 `COMMITTED`, 담당자 검토는 `WAITING_APPROVAL`이다. 같은 변경을 다시 보내도 새 DAG가 생기지 않는다.
4. `후속 검사와 검토 메모`에서 `현재 검토 대상 불러오기`를 누르면 문서 해시, 방법 버전, 각 산출물과 Evidence를 볼 수 있다. 판단 근거를 입력하고 `검토 완료 기록` 또는 `보완 요청 기록`을 직접 선택한다. 이는 사람의 검토 이력을 기록하는 동작이며 정책을 적용하거나 `REVIEW_REQUIRED` 상태를 변경하지 않는다. 별도의 메모만 남길 수도 있다.
5. 기록은 사람 Run과 증거로 보존되며 `이전 기록을 보존하고 재검토`로 다시 열 수 있다. 근거가 변경되면 기존 판단은 이전 기록이 되고 새로운 근거를 다시 확인해야 한다.
6. `같은 작업 재검증`을 누르면 기존 버전 문서를 OpenSearch에서 다시 조회하고 같은 Work에 새 Run과 Evidence가 추가된다. 자동 후속 작업도 새 의존 결과를 고정해 다시 수행되며, 내용이 같은 기존 인덱스 버전은 덮어쓰지 않고 재사용한다. 실패한 후속 작업은 화면에서 재시도할 수 있고 이전 실행과 메모도 보존된다.

VOC 회귀 검사는 고정된 합성 사례의 분류 결과 비교다. 정책 문구가 분류 결과에 미치는 인과관계, 정책 해석의 정확성 또는 법규 준수를 검사하지 않는다. VOC 분석 방법을 적용하거나 롤백하면 이 회귀 Work는 새 방법으로 다시 실행된다.

## 3. TASK-003: 피드백과 동일 조건 평가

1. TASK-003을 실행하고 추천 3개, 각 VOC ID와 가상 서비스 문서 ID, 미분류 항목과 검증 결과를 확인한다. 문서의 ID·버전·해시와 검색 결과를 검사하지만 추천 내용의 의미적 타당성은 검증하지 않는다. 첫 검증 보고서에는 이전 보고서가 없다고 표시되고, 다음 보고서부터 이전 검증 보고서의 같은 범주·새 범주를 표시하며 이전 근거를 열 수 있다. 범주 일치는 의미상 중복 판정이 아니다. 규정 변경 후라면 보고서에도 `REVIEW_REQUIRED`가 표시된다.
2. `누락 보완 후보`를 선택하고 추천에 피드백을 남긴 다음 `동일 평가 실행`을 누른다. 24건의 가상 고정 평가에서 Champion은 18/24, 후보는 24/24이며 개별 예측과 퇴행·개선 사례를 열어볼 수 있다. 별도 회귀 사례 6건도 같은 두 방법으로 검사한다.
3. `적용`을 직접 누른 뒤 다시 실행하면 `challenger-v2`가 사용된다. `이전 방법으로 롤백` 후 다음 실행은 다시 `champion-v1`이다.
4. 현재 방법으로 다시 실행한 뒤 `퇴행 후보 테스트`를 선택해 피드백을 남기고 평가하면 퇴행 3건, FAIL이다. 적용은 비활성화되며 `기각`할 수 있다.
5. `별도 회귀셋 차단 후보`는 기본 24건에서는 24/24지만 별도 회귀셋에서 2건 퇴행하므로 FAIL이다. 후보와 두 평가셋은 데모용으로 미리 정의되어 있다.

수치는 고정된 합성 사례에서 실제로 계산한 데모 결과다. 모델 성능 향상이나 실제 고객 유용성의 증거는 아니다. 참조 규정이 바뀌거나 활성 방법이 변경된 뒤에는 이전 보고서·개선안을 현재 조건의 증거로 재사용할 수 없다.
